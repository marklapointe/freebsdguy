# 4.2 Design Practices — Factory, Builder, and TAOCP

These practices apply to all remaining implementation tasks.

## 1. Gang of Four patterns we use deliberately

### Factory Method / Abstract Factory

**When:** Creating one of several related implementations from a discriminator (provider, env, role).

**Where in MDWeb:**

| Factory | Discriminator | Products |
|---------|---------------|----------|
| `AIServiceFactory` (exists) | `ollama` \| `openai` | `AIService` implementations |
| `JwtSecretFactory` | env / config / insecure | resolved secret or hard failure |
| `RoleGuardFactory` | role names | Express middleware |
| (later) `PortLayoutFactory` | install mode | FreeBSD path layout |

**Rules:**

- Factories return **interfaces/abstract types**, not concrete classes at call sites.
- Factories enforce **preconditions** (missing provider → throw with clear message).
- No “god factory” that builds the whole app; one family of products each.

### Builder

**When:** Assembling a complex object with many optional fields, validation at `build()`, or a **projection** of a larger structure (public config from full config).

**Where in MDWeb:**

| Builder | Builds | Why |
|---------|--------|-----|
| `PublicConfigBuilder` | Safe JSON for `GET /api/config` | Guarantees secret invariants |
| `PostWriteBuilder` | Frontmatter + body for disk | Validated slug/title/summary |
| `UploadOptionsBuilder` | Multer limits + filters | Centralized upload policy |
| `RegressionContextBuilder` (scripts) | Host/port/mode for test rounds | Avoid flag soup |

**Rules:**

- Fluent setters return `this`.
- `build()` is the only place that produces the object; it validates **invariants**.
- Builders are pure where possible (no I/O in `build()` except explicit “persist” steps).

### Other patterns only when earned

- **Strategy:** AI summarize/enhance already is strategy via `AIService`.
- **Singleton:** `SiteConfig` on the client already; do not add more without need.
- Skip Abstract Factory of Factories, Visitor, etc. — YAGNI.

## 2. Practices from Knuth / TAOCP (applied, not cosplay)

TAOCP is about **precise algorithms, data structures, and correctness**. We adopt the engineering habits that transfer to application code:

### 2.1 Stepwise refinement

Decompose until each unit has:

1. A single responsibility  
2. Named preconditions and postconditions  
3. A size that fits in one mental “pass”

Example refinement chain for public config:

```text
GET /api/config
  → load full Config (I/O)
  → PublicConfigBuilder.from(config).build()  (pure projection)
  → res.json
```

### 2.2 Invariants (stronger than comments)

State facts that must **always** hold; enforce in builders/factories, test them.

| Invariant ID | Statement |
|--------------|-----------|
| INV-SEC-1 | Public API responses never contain `apiKey` or `jwtSecret` |
| INV-SEC-2 | Production process never signs JWT with the default insecure secret |
| INV-SEC-3 | Resolved filesystem targets for posts/images stay under their base directory |
| INV-AUTH-1 | Mutating content endpoints require role ∈ {admin, contributor} |
| INV-AUTH-2 | Global theme mutation requires role = admin |

### 2.3 Algorithms as pure, named predicates

Path safety is a small graph/string algorithm — keep it pure and tested:

```text
isSafePath(base, target) ⇔
  resolve(target) is equal to resolve(base) OR a proper descendant
```

No side effects; complexity O(path length). Document the rule once; call from all routes.

### 2.4 Correctness before optimization

Knuth: *“premature optimization is the root of all evil.”*

- Prefer clear O(n) scans (image manifest, post list) until measured need.
- Optimize package size / offline npm cache where it matters for FreeBSD builds.
- Do not micro-optimize React re-renders while secrets still leak.

### 2.5 Explicit data structures

| Concern | Structure | Reason |
|---------|-----------|--------|
| Image metadata | Map filename → record | O(1) lookup by name; iterate for MD5 scan |
| Roles | Closed enum / union | Finite set — table-driven allowlist |
| Rate limits | Config record | Tunable constants, not magic numbers in middleware |
| Theme tokens | Dict of CSS variables | Simple associative array |

### 2.6 Literate module boundaries

- Name modules after **what they guarantee** (`public-config`, `safe-path`, `jwt-secret`), not after frameworks.
- Prefer short functions with one return path for security code (easier to prove by inspection).

## 3. Checklist for each new module

- [ ] Is this a Factory (family of products) or Builder (assembled projection/options)?
- [ ] Are invariants listed and tested?
- [ ] Is the core decision a pure function?
- [ ] Any premature optimization?
- [ ] Does the name match the guarantee?
