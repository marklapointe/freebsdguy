# 2.1-MDWeb-Security

## Overview
This document outlines the security strategy for MDWeb, focusing on protecting user data, preventing unauthorized access, and ensuring the integrity of the application in a FreeBSD environment.

## 1. Infrastructure Security (FreeBSD Specifics)

### 1.1 User Separation
- **Requirement**: The application MUST run as a non-privileged user (e.g., `www`).
- **Status**: Currently implemented in `mdweb.rc`.
- **Hardening**: Ensure the `www` user has no shell and a restricted home directory.

### 1.2 File System Permissions
- **Requirement**: The application source code and `node_modules` SHOULD be read-only for the `www` user.
- **Writable Directories**: Only the following directories should be writable by `www`:
  - `/usr/local/www/MDWeb/server/config` (for `config.json` and `users.json`)
  - `/usr/local/www/MDWeb/server/posts` (for Markdown files and images)
  - `/usr/local/www/MDWeb/server/themes`
- **Mitigation**: Update the FreeBSD port to set correct ownership and permissions during installation.

### 1.3 Environment Secrets
- **Requirement**: Sensitive secrets MUST NOT be hardcoded or fall back to insecure defaults in production.
- **Implementation**: Use a dedicated environment file (e.g., `/usr/local/etc/mdweb.env`) or set variables in `/etc/rc.conf` via `mdweb_env`.
- **Secrets**: `JWT_SECRET`, AI API keys (if not in `config.json`).

## 2. Application Security (Express & Middleware)

### 2.1 Security Headers
- **Action**: Integrate `helmet` middleware.
- **Configuration**:
  - `Content-Security-Policy`: Define a strict CSP to prevent XSS. Allow only trusted sources for AI APIs and local assets.
  - `HSTS`: Enable HTTP Strict Transport Security (for HTTPS deployments).
  - `X-Frame-Options`: Set to `DENY` or `SAMEORIGIN`.

### 2.2 CORS Policy
- **Risk**: Current implementation uses `cors()` with default (permissive) settings.
- **Mitigation**: Restrict `Access-Control-Allow-Origin` to the specific domain where MDWeb is hosted.

### 2.3 Rate Limiting
- **Action**: Implement `express-rate-limit`.
- **Target Endpoints**:
  - `/api/login`: Strictly limit brute-force attempts.
  - `/api/ai/*`: Prevent abuse of AI API credits/tokens.
- **Environment Handling**:
  - Set `trust proxy` to `1` (or appropriate depth) to support deployment behind Nginx or other reverse proxies.
  - Disable IP validation (`validate: { ip: false }`) to avoid warnings in development environments like Vite.

### 2.4 Authentication Hardening
- **JWT Secret**: Enforce a strong, unique `JWT_SECRET` via environment variables. Remove the 'freebsd_guy_secret_key' fallback.
- **Password Hashing**: Continue using `bcrypt` with a minimum cost factor of 10 (currently used).
- **Admin Password**: Address the broken default admin login by providing a CLI tool or secure initialization process to set the admin password on first deploy.

## 3. Data & Secret Security

### 3.1 AI API Keys
- **Current Issue**: API keys are stored in `config.json` and processed by `sanitize-html` before saving, which can lead to corruption.
- **Mitigation**: 
  - Remove HTML sanitization for sensitive fields like `apiKey`.
  - Prefer environment variables for API keys in high-security environments.
  - If stored in `config.json`, ensure the file has `0600` permissions.

### 3.2 Post Data
- **Integrity**: Ensure that only authorized users (Admin/Contributor) can write to the posts directory.
- **Validation**: Server-side validation of file names (slugs) to prevent directory traversal.

## 4. Input Validation & Sanitization

### 4.1 XSS Protection
- **Markdown Sanitization**: Instead of sanitizing the raw Markdown string with an HTML sanitizer, sanitize the *output* of the Markdown-to-HTML conversion on the frontend, or use a Markdown-aware sanitizer on the server.
- **Metadata Sanitization**: Continue sanitizing `title`, `summary`, and other metadata, but move this logic to a centralized validation utility.

### 4.2 Directory Traversal
- **Action**: Standardize the check used in `server/index.ts`.
- **Pattern**: 
  ```typescript
  const safePath = path.resolve(baseDir, requestedFile);
  if (!safePath.startsWith(path.resolve(baseDir))) {
      throw new Error("Traversal attempt");
  }
  ```

## 5. AI Security

### 5.1 Prompt Injection
- **Context**: Users might try to inject prompts into post content that gets summarized.
- **Mitigation**: 
  - Use system prompts that explicitly define the scope of summarization.
  - Limit the input length passed to the AI service.

### 5.2 Token Usage Monitoring
- **Mitigation**: Log AI API usage to detect anomalies or cost spikes.
